## ここでのスプリントの仕組み

スプリントはテーマ単位のバッチ — 通常 3〜8 個の PR を1つのリリースとして一緒に着地させます。各スプリントは次を持ちます:

1. **テーマ** — 何が変わるかの1文の枠付け
2. **項目** — 選ばれた作業、追跡 issue / PR 付き
3. **スコープ外** — 明示的に先送りするものとその理由
4. **リスク** — 既知の鋭利な部分
5. **レトロ** — 出荷後、何を学んだか

計画されたスプリントに合わない外部コントリビューター PR は、個別のパッチバージョン（`v0.50.X`）としてリリースされます。スプリントは、項目が互いを補強する一貫したバッチのために留保されます。

## 計画の原則

**Phase-0 適合評価。** すべてのスプリント候補はまず限界便益スクリーンを通ります: これは実ユーザーにとってプロダクトを目に見えて良くするか、それとも得るより維持コストの高い表面積を加えるか? 5つの質問の適合スクリーン — need / shape / bloat / clutter / scope。

**吸収より救出。** コントリビューター PR が部分的またはスコープを誤っている場合、複数回のリベースを求めるより、良い部分を `Co-authored-by` 帰属付きでメンテナ側 PR に継ぎ合わせる方を優先します。PR がそのまま本当に出荷可能なときのみ丸ごと吸収します。

**独立レビューゲート。** 自作 PR は (a) マージ済みステージ diff に対する Opus アドバイザーパス、または (b) 別レビュアーからの独立レビュー、のいずれかが必要です。高リスクバッチ（大 LOC、セキュリティ、ロック、耐久性）は両方を受けます。

**PR ごとのリリース速度。** 単一 PR が実バグを修正しクリーンなレビューを受けたら、スプリントバッチを待たず同日に独自のパッチリリースとして出荷します。摩擦ゼロが目標 — スプリントバッチは恣意的なグループ化ではなく一貫性のために存在します。

**PR 途中での機能クリープなし。** コントリビューターがレビュー中にスコープ追加を提案したら、別 PR として起票し元からリンクします。現在の PR は元の境界を保ちます。

**リリース前ゲート（必須）。** すべてのリリースは次を実行:
1. `pytest tests/ -q --timeout=120` クリーン
2. ブラウザ健全性チェック（テストサーバーに対する HTTP レベル API テスト）
3. マージ済みステージ diff に対する Opus アドバイザーパス（書面ブリーフ付き）
4. CHANGELOG.md ＋ ROADMAP.md ＋ TESTING.md のバージョンスタンプ
5. Python 3.11 / 3.12 / 3.13 で CI グリーン

これらのいずれかをスキップするには、メンテナからの文書化された「オーバーライドを行う」が必要です。

## スプリントの形

典型的なスプリントは端から端まで 3〜7 日かかります:

| フェーズ | 期間 | 成果 |
|---|---|---|
| トリアージ | 0.5 日 | アクティブキュー → 選択項目 ＋ スコープメモ |
| 設計 / スパイク | 0.5〜1 日 | 必要な項目の設計メモ。先送りを文書化 |
| ビルド | 2〜4 日 | 各項目を独自ブランチ ＋ PR で独立レビュー |
| レビュー | 0.5〜1 日 | メンテナ ＋ Opus アドバイザーパス。SHOULD-FIX はリリース内で吸収 |
| ステージ ＋ 出荷 | 0.5 日 | ステージブランチ、完全テストスイート、リリース PR、タグ、デプロイ、ライブ検証 |
| 衛生 | 0.5 日 | PR / issue クローズ、GitHub リリースノート、ドキュメント同期、レトロ |

より小さいスプリント（1〜2 PR）は端から端まで 1〜2 日に圧縮されます。単一 PR リリースはステージブランチをスキップし、コントリビューターのブランチ（fork が書き込みアクセスを与えない場合はメンテナがリベースしたコピー）から直接リリース PR で出荷します。

## スプリント履歴

バージョンごとの詳細は [CHANGELOG.md](./CHANGELOG.md) にあります。高レベルのテーマ年代記は [ROADMAP.md → Sprint History](./ROADMAP.md#sprint-history) にあります。注目に値するいくつかのスプリント:

- **Sprint 19** — 認証 ＋ セキュリティハードニング。アプリを localhost を超えて起動したままにしても安全にした最初のスプリント。
- **Sprint 21** — モバイルレスポンシブ ＋ Docker。2コンテナ compose が最初のセルフホストデプロイの波を可能にした。
- **Sprint 22** — マルチプロファイル対応。大きな CLI 同等性の解放。プロファイル切り替えがサーバー再起動なしでシームレスに。
- **Sprint 25** — macOS デスクトップアプリケーション。ネイティブ Swift ＋ WKWebView シェル、ユニバーサル Intel ＋ Apple Silicon DMG、Sparkle 2 自動更新。別の `hermes-webui/hermes-swift-mac` リポジトリにある。
- **Sprint 26** — プラガブルテーマ。コミュニティコントリビューターが純粋な CSS としてテーマを追加できる CSS 変数駆動の8テーマシステム。
- **Sprint 34** — v0.50.0 UI 全面改修。コンポーザ中心のコントロール、Control Center モーダル、ワークスペース状態機械、rAF ストリーミングスロットル。

## スコープ外（全スプリント共通）

これらは意図的にロードマップに載せていません。計画サイクルを節約するためここに列挙します。

- **マルチユーザーコラボレーション** — コードベース全体が単一ユーザー前提。リファクタはゼロからのアーキテクチャ変更になる。
- **共有 / 公開会話 URL** — アクセス制御 ＋ CDN を伴うホステッドバックエンドが必要。セルフホストではスコープ外。
- **プラグインマーケットプレイス** — Hermes skills が既にこの面をカバー。
- **Anthropic / Claude 独自機能** — Projects の AI メモリ、Claude artifacts 同期。再現不可能。
- **Linux / Windows ネイティブアプリラッパー** — macOS は完了。他プラットフォームの需要は未確立。Web UI はどのブラウザでも動く。
- **App Store 配布** — サンドボックス化がローカルサーバーモデルを壊す。
- **Python ウェブアプリの自動更新機構** — Sparkle 2 が Mac アプリをカバー。ウェブアプリは `git pull` ＋ 再起動で更新し、他のあらゆる Python サービスと同じ。

## テンプレート

新しいスプリント計画を開くときは、この構造をコピーしてください:

```markdown
# Sprint NN — <theme>

**Version target:** vX.Y.Z
**Theme:** <single sentence>
**Date started:** YYYY-MM-DD
**Status:** PLANNED | IN PROGRESS | COMPLETED — vX.Y.Z

## Items
| # | Issue | Title | Complexity | Files | PR |
|---|-------|-------|------------|-------|-----|

## Rationale
Why these items, why now.

## Build approach
Per-item branch + PR; or single combined branch if items are tightly coupled.

## Out of scope
What did NOT make this sprint and why.

## Known risks
Sharp edges to watch during review.

## PR Status
| Issue | PR | Status |
|-------|-----|--------|

## Retro (post-ship)
What worked, what we'd do differently.
```

各スプリントのメンテナの計画メモはワークスペースリポジトリ（プライベート）にあり、このファイルにはありません。このファイルは公開向けの計画の形です。
