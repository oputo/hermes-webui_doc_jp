# コントリビューター

Hermes WebUI はコミュニティプロジェクトです。**194人** がリリースタグに着地したコードを送り出しました — バッチリリースに救い出された人や Co-authored-by トレーラーで吸収された人のロングテールを含みます。このファイルは正典のクレジットです。

コントリビューターの PR 数は、彼らがクレジットを得る個別 PR の数です: 直接マージされた自作 PR、クローズされたがリリースコミットに吸収された自作 PR（バッチマージ、救出書き直し、cherry-pick して帰属された作業）、そして `CHANGELOG.md` で明示的に帰属された PR。すべて同等に数えます。

**追跡されたコントリビューター総数:** 197
**PR クレジット総数:** 846
**最終更新:** v0.51.217、2026-06-02（帰属の backfill — CONTRIBUTORS.md エントリを欠いていた吸収 PR コントリビューター3名。PR 説明を参照）

メンテナワークスペースの `scripts/regen_contributors.py` で生成。3 つのソースを合算します: GitHub のマージ済み PR リスト、`CHANGELOG.md` の帰属行、master に着地したコミットの `Co-authored-by:` トレーラー（コミットが cherry-pick され帰属された CLOSED な PR の正典シグナル）。名前が欠けているか誤っている場合は `CONTRIBUTORS.md` に PR を開いてください — 各リリースで changelog と相互チェックします。

## クレジットの追跡方法

このリポジトリのほとんどの PR は次の4経路のいずれかで着地します:

1. **直接マージ** — PR がレビューされ単独でマージされる。作者が `git log` と PR の `merged_at` タイムスタンプに直接現れる。
2. **バッチリリースへの squash** — PR が他の数件のコントリビューター PR と共に単一のリリースコミットにマージされる（例: `release: v0.51.55 — 9-PR contributor batch`）。元の PR は GitHub 上でクローズ（マージではない）するが、squash されたリリースコミットが `Co-authored-by: <you>` トレーラーと、ユーザー名・PR 番号であなたをクレジットする `CHANGELOG.md` のエントリを持つ。
3. **より大きな PR からの救出** — PR が1つの良い変更を無関係/危険なものと混ぜている場合、分割します: 良い部分はクリーンなフォローアップ PR で出荷され、あなたは CHANGELOG エントリでクレジットされ、元の PR はどこに何が行ったかを示す救出マップ付きでクローズされる。
4. **自動リベース ＋ 自動修正** — 機械的なブロッカー（CHANGELOG コンフリクト、lint、ずれたテスト）を持つマージ可能なコントリビューター PR では、メンテナがコントリビューターのブランチをリベースし、ブロッカーを修正し、force-push で戻します。`Co-authored-by` トレーラーがあなたの作者性を保ちます。

4 経路すべてが貢献として数えられます。GitHub の `merged_at` フィールドは経路 1 しか捕捉しません。経路 2〜4 は作業が master でライブでも、コントリビューターの PR 上では「closed」と表示されます。だからこのファイルは GitHub のマージ済み PR リストだけでなく CHANGELOG の帰属行を参照します。
