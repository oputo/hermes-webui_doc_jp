# Hermes WebUI へのコントリビュート

コントリビュートありがとうございます。

Hermes WebUI は意図的に取り組みやすく作られています。サーバーは Python、ブラウザは vanilla JS、ビルドステップなし、バンドラなし、フロントエンドフレームワークなし。最良の pull request は、その単純さを保ちつつ、実際の問題をきれいに解決します。

## 始める前に

- AI アシスタントが変更を行う・手伝う場合は [`AGENTS.md`](AGENTS.md) を読む。
- 触れるサブシステムについて [`docs/CONTRACTS.md`](../docs/CONTRACTS.md) とリンクされた contract/RFC を読む。
- UI や UX 作業では [`docs/UIUX-GUIDE.md`](../docs/UIUX-GUIDE.md) と [`DESIGN.md`](DESIGN.md) を読む。
- ランタイム、ストリーミング、復旧、リプレイ、圧縮、コンテキスト再構築、セッションメタデータの作業では、[`docs/rfcs/README.md`](../docs/rfcs/README.md) とそこに列挙された関連 RFC から始める。

これらのドキュメントをレビューのガードレールとして使ってください: 変更をスコープ内に保ち、no-build-step アーキテクチャを維持し、挙動変更時に docs/changelog を更新し、UI 変更には UI エビデンスを含め、実用的な範囲で挙動変更にテストを追加する。

### コントラクトに影響する PR

コントラクトに影響する PR とは、公開コントラクト文書、RFC、コントリビューターガイド、プロダクトセマンティクステスト、またはそれらの文書が既に記述する挙動を更新する変更です。これらの PR は、触れたコントラクトファミリーと使用したエビデンスを示す明示的な `Contract Routing` セクションを PR 本文に必要とします。短いルーティングの形は [`docs/CONTRACTS.md#contract-routing`](../docs/CONTRACTS.md#contract-routing)、意図的なコントラクト変更は [`docs/CONTRACTS.md#contract-changes`](../docs/CONTRACTS.md#contract-changes) を参照。

PR が既存のコントラクトを意図的に変更する場合、旧ルール・新ルール・変更が正当な理由を述べる `Contract Change` セクションを追加してください。テストだけを変えてプロダクト挙動を黙って再定義しないでください。対応する docs を同じ PR で更新してください。

リリースバッチは、コード diff が小さく CI がグリーンでも、含まれるコントラクト影響 PR を通常の修正とは別に呼び出すべきです。

## 強い Pull Request への2つの道

### 道1: 小さく焦点を絞った変更

これがレビューとマージへの最速の道です。

- 1つの明確なバグを修正、または1つの厳密にスコープされた改善を追加
- できるだけ少ないファイルに触れる
- 機能変更に混ぜたついでのリファクタを避ける
- PR を開く前に該当テストをローカルで実行
- PR 説明を簡潔・具体的に保つ

これらはレビューが最も容易で、すばやく安全にマージできる変更です。

### 道2: より大きな変更

アーキテクチャを変える、ワークフローを作り直す、実質的な UI 機能を追加する、コア挙動を変える場合は、まず方向性をすり合わせてください。

- 早めに issue を開く、議論を始める、または draft PR を開く
- 欲しい実装だけでなく、解決しようとしている問題を説明する
- トレードオフ、移行リスク、検討した代替案を呼び出す
- 無関係な作業を分離して最終 PR をレビューしやすく保つ

大きな変更は歓迎ですが、不意打ちの書き直しはうまくレビューしづらいです。

## すべての PR に期待すること

### 1. PR ごとに1つの論理変更

各 PR を焦点を絞って保つ。関連する小さな修正グループは構いません。バグ修正 ＋ CSS クリーンアップ ＋ リファクタ ＋ docs 書き直しはダメです。

### 2. ローカル検証

テストスイートをローカルで実行:

```bash
pytest tests/ -v --timeout=60
```

CI もこのスイートを Python `3.11`、`3.12`、`3.13` で実行します。

変更がブラウザ挙動に影響するなら、[TESTING.md](TESTING.md) の該当する手動チェックも実行してください。

### 3. 明確な PR 説明

現在このリポジトリに PR テンプレートはないので、重要なセクションを自分で含めてください:

- Thinking Path
- What Changed
- Why It Matters
- Verification
- Risks / Follow-ups
- Model Used

変更がユーザー可視なら、スクリーンショットまたは短い動画を含める。

UI や UX 変更では、before/after 画像が必須です。before/after 画像なしでインターフェースや対話フローを変える PR は、そのエビデンスが追加されるまで意味あるレビューを受けられないことがあります。

### 4. AI 利用の開示

AI が変更の作成を手伝ったら、PR 説明にそう記してください。

含めるもの:

- プロバイダー
- 正確なモデル名または ID
- 重要だった注目すべきモードやツール利用

AI を使わなかった場合は次を記す: `None — human-authored`。

### 5. docs を正直に保つ

変更が挙動、アーキテクチャ、テスト、セットアップ、ユーザー向けワークフローを変えるなら、関連する docs を同じ PR で更新してください。

よくあるファイル:

- セットアップ・利用・コントリビューター向けコマンドは [README.md](README.md)
- 出荷済み機能とスプリント履歴は [ROADMAP.md](ROADMAP.md)
- 実装詳細と設計制約は [ARCHITECTURE.md](ARCHITECTURE.md)
- 手動・自動検証ガイダンスは [TESTING.md](TESTING.md)
- メンテナがリリースノート用エントリを望むときは [CHANGELOG.md](CHANGELOG.md)

## プロジェクト固有のガイドライン

### 設計制約を維持する

Hermes WebUI は意図的に:

- ビルドステップなし
- バンドラなし
- フロントエンドフレームワークなし
- ターミナルから変更が容易

得られるものが明確でトレードオフが正当でない限り、新しいインフラや依存を導入しないでください。

### コードベースの既存の形に合わせる

- サーバーロジックは `api/` に。`server.py` は薄いまま
- フロントエンド挙動は既存の `static/*.js` モジュールに
- 並行する抽象を導入するより現在のパターンを拡張する方を優先
- ターミナルからリポジトリで直接作業する将来のコントリビューターに読みやすく保つ

### ユーザー向け変更には慎重に

このプロジェクトは UI 主導が強いです。対話フロー、セッション挙動、ワークスペース参照、オンボーディング、モバイルレイアウトを変えるなら:

- ハッピーパスをテスト
- 該当時は再読み込み挙動をテスト
- 該当時は狭幅/モバイルレイアウトをテスト
- PR に before/after 画像を含める

### セキュリティと安全性が重要

このアプリはワークスペース内容を露出し、エージェントアクションを実行し、任意でリバースプロキシや Docker デプロイの背後に置けます。認証、パス処理、アップロード、ストリーミング、環境処理を高リスク領域として扱ってください。

PR がセキュリティに敏感な挙動に触れるなら、PR 説明で明示し、どう検証したか説明してください。

## 良い PR メッセージの書き方

プロジェクト目標から具体的な修正までの連鎖を説明する短い Thinking Path から始めてください。

例:

> - Hermes WebUI はブラウザで Hermes CLI とほぼ 1:1 同等を目指す
> - 長時間のチャットターンは SSE ストリーミングとセッション復旧に依存する
> - 処理中のターン中に再読み込みすると UI が不整合状態に陥り得る
> - バグは、復旧したセッションがメッセージは復元するがライブストリーム状態を復元しなかったこと
> - この PR は復旧経路を修正し、再読み込み後に処理中ターンがきれいに再接続するようにする
> - 便益は、ユーザーがアクティブな作業の可視性を失わずに更新・再接続できること

別の例:

> - Hermes WebUI は意図的にシンプルな Python ＋ vanilla JS アプリケーション
> - 右パネルはワークスペース参照とプレビューに使う
> - モバイルでは、パネル状態の変化が明白でタッチしやすい必要がある
> - 既存のクローズ操作はボトムナビフローと不整合だった
> - この PR はモバイルパネルのクローズ挙動を修正し、現在のナビゲーションモデルに整合させる
> - 結果としてスマホでの行き止まり UI 状態が減る

その後、次を扱う:

- 何を変えたか
- なぜ変えたか
- どう検証したか
- どんなリスクが残るか

## レビューのコツ

最もスムーズなレビューが欲しいですか?

- diff をタイトに保つ
- 物事に明確な名前を付ける
- 不要な書き直しを避ける
- コードがさもなくば追いづらい箇所にのみ短いコメントを追加
- レビューフィードバックに直接応答し、スコープが変わったら PR 説明を更新
