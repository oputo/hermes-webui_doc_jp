# UI/UX ガイド

このドキュメントは、リポジトリに既に表れている UI/UX の原則をまとめたものです。新しいデザイン提案ではなく、コントリビューター向けのガイドです。出典には [`DESIGN.md`](../root-docs/DESIGN.md)、[`README.md`](../root-docs/README.md)、[`THEMES.md`](../root-docs/THEMES.md)、[`docs/ui-ux/index.html`](ui-ux/index.html)、[`docs/ui-ux/two-stage-proposal.html`](ui-ux/two-stage-proposal.html)、および `static/style.css` 内のデザインコメントが含まれます。

レイアウト、チャット描画、コンポーザ周り、ナビゲーション、テーマ/スキンの挙動、レスポンシブ挙動、視覚的階層に触れる変更ではこのガイドを使ってください。純粋なバックエンド変更には、代わりにランタイム/状態のコントラクトを使ってください。

## プロダクトの形

Hermes WebUI は Hermes Agent のためのブラウザワークベンチで、ほぼ CLI 同等の機能と、シンプルな実装形態を持ちます。サーバーは Python、ブラウザは vanilla JavaScript、ビルドステップなし、バンドラなし、フロントエンドフレームワークなし。

主要レイアウトは3ペインです:

- セッションとナビゲーション用の左サイドバー、
- チャット用の中央パネル、
- ワークスペースのファイル参照とプレビュー用の右パネル。

モデル、プロファイル、ワークスペース、添付、音声入力、コンテキスト使用量、Stop、Send のコントロールはコンポーザのフッターにあります。設定とセッションレベルのツールは Hermes Control Center にあります。変更が別の対話モデルを明確に正当化しない限り、この形を保ってください。

## 中核の感触: 静かな開発者コンソール

主役は会話です。ツール呼び出し、思考トレース、コンテキスト圧縮記録、トークン使用量、ランタイムステータス、その他の内部情報は有用ですが、トランスクリプトのメタデータです。視覚的優先度では、ユーザーとアシスタントの文章より下に置くべきです。

推奨:

- 静かなサーフェス、
- 明確な余白、
- 控えめなアクセント使用、
- デバッグ詳細の段階的開示、
- 装飾的なクロムより読みやすいテキスト。

インターフェースをカラフルなカードのデモページに変えないでください。エラー、承認、その他のアクション必須状態は、ユーザーが気づいて反応しなければならないため目立ってよいです。

## 会話の階層

チャットのターンは1つの一貫した物語として読めるべきです:

1. ユーザーメッセージ: 右寄せのコンパクトな吹き出し。
2. アシスタントコンテンツ: 左寄せ、文章優先、重い吹き出しにしない。
3. ツール・思考・進捗・コンテキストのトレース: アシスタントターンの内部または隣接の静かな開示行。
4. 生ログと冗長な詳細: 明示的に展開するまで隠す。

すべての内部イベントを第一級のチャットカードとして描画しないでください。多くのツールを使ったターンは、作業を検査可能なアクティビティとして要約すべきで、無関係に見えるカードの山をユーザーに読ませるべきではありません。

## ツール・思考・アクティビティのトレース

ツールカードはデバッグイベント行であり、チャットメッセージではありません。アイコン、名前、短いターゲットまたはプレビュー、ステータスを最初に表示します。引数、結果スニペット、長いログは展開の背後に置き、結果スニペットは切り詰め、必要に応じて完全な出力は show-more の背後に置きます。

思考カードとコンテキストカードは、静かなメタデータの視覚ファミリーを共有すべきです。アシスタントの文章を圧倒すべきではありません。折りたたまれたアクティビティ要約は簡潔であるべきで（例: `Activity: 4 tools`）、思考エリアを重複させたり、要約にすべてのツール名を列挙したり、冗長な末尾のカウントバッジを追加したりすべきではありません。

可視の途中アシスタント進捗は、生のデバッグ詳細ではなく、ライブ会話タイムラインの一部です。Compact Activity はツール引数、長いツール結果、低レベルの推論詳細を折りたためますが、簡潔なユーザー可視の進捗テキストを折りたたまれた開示の中でしか見られないようにしてはいけません。

`docs/ui-ux/two-stage-proposal.html` の既存の2段階提案は、長いターンに対する互換性のある方向性を記録しています。ライブ作業は worklog としてグループ化でき、その後落ち着いた履歴は折りたたまれ、最終回答が静かな結論として読めます。そのページは既存の提案として扱い、コードとテストが実装を証明しない限り、出荷済みの挙動として扱わないでください。

## タイポグラフィとコンテンツ

スプリットタイポグラフィを意図的に使ってください:

- アシスタントの文章はデフォルトで UI の他の部分と同じシステムサンス stack を使う（`static/style.css` の `--font-ui`）、
- 編集的なセリフのアシスタント文章は歴史的/提案的、またはスキンスコープ限定。明示的なデザイン承認＋コードとテストの証拠なしに、グローバルなアシスタントセリフを再導入しない、
- ユーザー吹き出しと機能的 UI も、スコープされたスキンが意図的にタイポグラフィを上書きしない限りシステムサンス stack を使う、
- monospace はコード、ファイルパス、コマンド、ツール名、コンパクトなメタデータ用。

スケールはタイトに保ってください。既存のトークンで足りるなら、ほぼ重複する一回限りのフォントサイズ、色、radius 値、spacing 値の導入を避けてください。

## 色・奥行き・形

アクセントは一度に1つ。セマンティックカラーはセマンティックな状態用: success、warning、error、info。同じビューポート内で多くの明るい色を装飾的に混ぜないでください。

トランスクリプトではほぼ影を使いません。影はポップオーバー、ドロップダウン、モーダル、フローティングコントロールに留保します。チャットカードは通常、控えめなボーダーか控えめな tint のどちらかを使うべきで、両方の強い組み合わせは避けます。

入れ子の角丸長方形の積み重ねを避けてください。行とリスト項目はコンパクトに感じさせ、パネルとカードはやや丸くてよく、真の pill はチップとバッジに留保します。

## コンポーザとコントロール

コンポーザはコマンドサーフェスです。読みやすく、安定し、集中させてください:

- 通常コントロールに大げさなホバースケーリングをしない、
- モデル/ワークスペース/プロファイルのコントロールを混雑させる環境的クロムを置かない、
- 明確な価値のトレードオフなしに、窮屈なレイアウトへ新しいフッターボタンを追加しない、
- 入力中に Stop/Send とコンテキストフィードバックを見つけやすく保つ。

コントロールを追加するときは、ワイドデスクトップとモバイルの両方でユーザーがどこで見つけるか考えてください。設定やクォータ/コントロールサーフェスがコンポーザに収まらない場合は、フッターに押し込むのではなく適切な Control Center パネルへ回してください。

## レスポンシブ挙動

モバイルは後付けではありません。リポジトリは、ハンバーガーサイドバー、モバイルでアクセス可能な上部タブ、右端のファイルスライドオーバー、スマホでの全高チャット/コンポーザ挙動、タッチしやすいコントロールを伴うレスポンシブレイアウトを文書化しています。

UI 変更では、関連する状態を検証してください:

- ワイドデスクトップ、
- 通常のラップトップ幅、
- 狭い/モバイル幅、
- 該当時はサイドパネルの開閉、
- 該当時は長いチャットコンテンツとライブストリーミング。

コントロールはタッチサイズで使い続けられるべきで、モバイルナビゲーションは不必要にチャットの高さを奪うべきではありません。

## テーマとスキン

テーマとスキンの作業は既存の変数システムを使うべきです。`THEMES.md` は `static/style.css` の中核パレット変数を指し、CSS 内のスキンコメントは、完全なパレット書き換えとアクセントのみの変更の期待パターンを示します。

現在の実装には、`static/boot.js` から取得される2つの外観軸があります。`theme` は `light`、`dark`、`system` のみで、ダークモードでは `.dark` クラスに解決されます。`skin` は `data-skin` で適用される別の軸で、現在 `default`、`ares`、`mono`、`slate`、`poseidon`、`sisyphus`、`charizard`、`sienna`、`catppuccin`、`nous`、`geist-contrast` / Geist Contrast を含みます。`slate` はアクティブなスキンであると同時にレガシーなテーマ名の移行先でもあります。`solarized`、`monokai`、`nord`、`oled` は、現在のテーマ/スキンペアにマップされたレガシーなテーマ名です。現在の `static/boot.js`、`static/index.html`、`static/style.css` のコントラクトが依然それをサポートすると先に証明せずに、古い `data-theme` のみのガイダンスに従わないでください。

トークンや既存変数が意図を運べるのに、孤立したコンポーネントへ新しい色、radii、shadow、タイポグラフィ値をハードコードしないでください。トークンが欠けている場合は、なぜ新しいものが必要かを説明してください。

## UI 変更に期待される証拠

あらゆるインターフェースまたは対話の変更について:

- before/after 画像または短い動画を含める、
- テストしたビューポートサイズとレスポンシブ状態に言及する、
- 該当時は影響を受ける視覚インベントリまたはデザイン出典を参照する、
- 実用的な範囲で、挙動・状態の永続性・回帰しやすい DOM 構造のテストを追加または更新する、
- 将来の視覚回帰テストに役立つ安定したクラスまたは data フックを保つ。

## Do / Don't まとめ

Do:

- 会話を主役に保つ、
- 落ち着いたらノイジーな内部情報をデフォルトで折りたたむ、
- デバッグ詳細を、視覚的に支配的にせずアクセス可能にする、
- 既存のトークン・変数・コンポーネントパターンを使う、
- エラーや承認などのアクション必須状態を守る。

Don't:

- すべてのツール呼び出しを別個のチャットメッセージのように見せる、
- ユーザー向けの理由なしに装飾的な色や動きを追加する、
- 通常の UI 作業のためにフロントエンドフレームワーク・バンドラ・ビルドステップを導入する、
- 重要な復旧・エラー・承認状態を隠す、
- コード/テストの証拠なしに提案モックアップを出荷済み挙動として扱う。
