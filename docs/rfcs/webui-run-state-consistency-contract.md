# WebUI Run 状態一貫性コントラクト

- **Status:** Proposed
- **Author:** @franksong2702
- **Created:** 2026-05-16
- **Tracking issue:** [#2361](https://github.com/nesquena/hermes-webui/issues/2361)
- **Related architecture:** [#1925](https://github.com/nesquena/hermes-webui/issues/1925), [`hermes-run-adapter-contract.md`](hermes-run-adapter-contract.md)

## Problem

1つの WebUI エージェントターンは、複数の重なり合う状態レイヤーで表現されます:

- ユーザーが読める可視トランスクリプト、
- エージェントが実際に受け取るモデルコンテキスト / `context_messages`、
- `pending_user_message` とアクティブストリームメタデータ、
- ライブ SSE イベントとインメモリストリーム状態、
- 耐久的な run journal / replay 状態、
- 自動圧縮サマリーとアクティブタスクのハンドオフテキスト、
- ブラウザのライブタイムライン DOM/キャッシュ、
- サイドバー順序、未読状態、`updated_at` メタデータ。

これらのレイヤーは独立していません。互いにドリフトすると、ユーザーは無関係に見える失敗を目にします: プロンプトが可視なのに復旧されたモデルコンテキストから欠ける、セッション切り替え後にライブ run が thinking/tool カードを失ったり並べ替えたりする、クリーンアップが古いセッションを新しくアクティブに見せる、replay が内容を重複させる、自動圧縮の参照素材がアクティブターン内に現れる。

この RFC は、それらのレイヤーの一貫性コントラクトを定義します。#1925 のより大きな run adapter の方向性を補完し、WebUI が依然複数の重なる状態ストアを持つ間、何が一貫し続けねばならないかを文書化します。

## Goals

- アクティブおよび復旧された WebUI ターンに関与する状態レイヤーを定義する。
- 各レイヤーの source-of-truth 期待を明示する。
- ストリーミング、replay、圧縮、復旧、モデルコンテキスト、サイドバーの変更にレビュアー向けチェックリストを与える。
- 最近の実 issue を再利用可能な不変条件にマップし、将来の修正が同じクラスのバグを症状ごとに1つずつ解決しないようにする。

## Non-goals

- ここでランナープロセス、サイドカー、新ランタイム境界を実装しない。
- #1925 や run adapter コントラクトを置き換えない。
- この RFC でストリーミングプロトコルを書き直さない。
- 既に修正された狭いバグを再オープンしない。
- 無関係な UI 磨き込みの何でも入れにしない。

## State Layers

| レイヤー | 目的 | source-of-truth 期待 | してはいけないこと |
|---|---|---|---|
| 可視トランスクリプト | ユーザーとアシスタントが言ったことを表示 | セッショントランスクリプト＋ライブ replay が1つの時系列のユーザー可視物語を生むべき | アクティブな作業を開始したユーザーターンを隠す、または内部復旧テキストを現在のユーザー意図として表示する |
| モデルコンテキスト / `context_messages` | 会話状態をエージェントに供給 | ユーザー可視の理由で意図的に除外しない限り、現在の可視ユーザーターンを含む必要がある | ユーザーが見えるものと矛盾するコンテキストからエージェントを再開させる |
| 保留ターンメタデータ | 送信済みだが未確定のユーザー入力を橋渡し | アクティブな作業を所有するユーザーターンとストリームを識別する必要がある | 復旧後に恒久的な重複トランスクリプト行になる |
| ライブストリーム / SSE | アクティブなランタイムイベントをブラウザに配信 | 観測経路のままであるべきで、既に発行されたイベントの唯一の耐久真実ではない | 再読み込み、再接続、セッション切り替えで可視シーンを失う |
| Run journal / replay | 再接続や再起動後に発行済みランタイムイベントを再構築 | カーソル安全かつ冪等であるべき | アシスタントテキスト、thinking テキスト、ツールカード、圧縮カードを重複させる |
| 圧縮サマリー / ハンドオフ | 自動圧縮後にエージェントに復旧コンテキストを与える | 明示的に履歴として描画されない限り、エージェント向け復旧素材のままであるべき | アクティブターンを汚染する、または暗黙の現在ユーザー意図になる |
| ライブ UI シーン/キャッシュ | 展開行、進行中カード、ローカルスクロール、一時グループ化を保持 | 表現を最適化してよいが、トランスクリプト/replay から再構築または降格可能であるべき | 時系列順序が存在する唯一の場所になる |
| サイドバー/セッションメタデータ | ユーザーがアクティブ・最近のセッションを見つけるのを助ける | 意味あるユーザーまたはアシスタントの活動を反映する必要がある | バックグラウンドクリーンアップを新鮮なユーザー向け更新として扱う |

## Core Invariants

1. **可視の現在ターンはモデルコンテキストに入る。** ユーザーが現在のプロンプトを見られ、WebUI がモデルにその作業の継続を求めるなら、WebUI が除外した明示的理由を示さない限り、そのプロンプトは再構築されたモデルコンテキストに含まれる必要がある。
2. **アクティブターン UI はその所有者を保つ。** アクティブな作業を開始したユーザーターンは、その作業に属するアシスタントテキスト、thinking カード、ツールカード、活動グループの前に可視のままであるべき。
3. **再アタッチは順序を保つか明確に降格する。** 再読み込み、再接続、セッション切り替えは時系列のライブシーン順序を保つべき。正確なライブシーンを復元できないなら、内容を黙って並べ替えるのではなく、明示的な構造化 replay 状態に降格すべき。
4. **メンテナンスは活動ではない。** stale-stream クリーンアップ、孤児修復、バックグラウンド圧縮のようなランタイムメンテナンスは、ユーザーやアシスタントが今行動したかのようにサイドバー順序、未読マーカー、アクティブセッション操作をリフレッシュすべきではない。
5. **Replay は冪等。** カーソルからの run の replay は、トランスクリプト行、thinking 内容、途中アシスタントテキスト、ツールカード、圧縮カードを重複させてはならない。replay された長タスクイベントはライブ SSE イベントと同じブラウザ向けタイムラインレンダラに入り、復旧が構造化された Thinking / progress / tool / compression ターンを別個のフラット化された表現に降格しないようにすべき。可視の途中アシスタント進捗は可視のタイムラインコンテンツのままであるべき。コンパクトな Activity 開示が隣接するツール/デバッグ詳細を要約してよいが、それが発行済み進捗テキストをユーザーが見られる唯一の場所であってはならない。
6. **圧縮は現在の意図ではない。** 自動圧縮サマリーと参照カードは復旧/ハンドオフ素材。新しいユーザーリクエスト、アクティブターン内容、現在の回答のデフォルト可視説明として扱ってはならない。
7. **観測には降格経路がある。** 長時間または多数セッションの観測は、UI が沈黙して見えず、通常 API がアクティブストリームの背後で停滞しないよう、十分なハートビート/降格ステータスを公開すべき。
8. **すべての変更はそのレイヤーを名指す。** ストリーミング、復旧、コンテキスト再構築、圧縮、replay、サイドバーメタデータに触れる PR は、どのレイヤーを変えるか、どの回帰が不変条件が依然成立すると証明するかを述べるべき。

## Review Checklist

run 状態、ストリーミング、replay、圧縮、コンテキスト再構築、セッションメタデータに触れる PR にこのチェックリストを使う:

- この PR はどの状態レイヤーを読み書きするか?
- この変更後、どのレイヤーが source of truth か?
- 可視トランスクリプトとモデルコンテキストが乖離し得るか? そうなら、それは意図的でユーザー可視か?
- ブラウザ再読み込み、セッション切り替え、SSE 再接続、WebUI 再起動の後に何が起きるか?
- Replay は重複なしに同じシーンを再構築するか?
- Replay は thinking、途中アシスタントテキスト、ツールカード、圧縮カード、終端状態にライブ SSE と同じタイムライン描画経路を使うか?
- この変更は、意味あるユーザーまたはアシスタントの活動なしにサイドバーでセッションを動かし得るか?
- 自動圧縮や復旧テキストが可視のアクティブターン内容になり得るか?
- どのテストまたは手動証拠が不変条件を証明するか?

## Run Adapter RFC との関係

run adapter RFC は、WebUI と Hermes ランタイム所有権の、より長期的なイベント/制御境界を定義します。この RFC は、現在の WebUI と将来のアダプタバック実装が保つべき一貫性ルールを定義します。

2つのドキュメントは一緒に読むべきです:

- アダプタコントラクトが答える: 「実行所有権はどこに置くべきか?」
- この一貫性コントラクトが答える: 「実行がアクティブまたは復旧中の間、トランスクリプト、コンテキスト、ストリーム、replay、圧縮、UI メタデータはどう一貫を保つか?」

## Rollout Plan

1. この RFC をレビュー可能なドラフトとして着地させ、PR 議論を通して洗練する。
2. 将来のストリーミング/復旧/圧縮/サイドバー PR を、意図的に保つか変える不変条件にリンクし戻す。
3. 繰り返すチェックリスト項目を、実用的な範囲で焦点を絞った回帰テストに変換する。
4. #1925 が新しいアダプタバックのランタイムレイヤーを導入するなら、この RFC を更新するか受理された実装コントラクトで置き換え、これらの不変条件が歴史的議論にのみ存在しないようにする。
