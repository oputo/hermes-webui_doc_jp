# RFC: クラッシュ安全なチャット送信のための WebUI ターンジャーナル

- **Status:** Proposed
- **Author:** @ai-ag2026
- **Created:** 2026-05-11

## Problem

WebUI のチャットターンは複数の耐久性境界を横断します:

1. ブラウザがユーザーメッセージを送信、
2. WebUI がセッションランタイムメタデータを作成/更新、
3. エージェントワーカーがストリーミングを開始、
4. アシスタント出力が追記される、
5. JSON サイドカーと派生インデックスが保存される。

送信から最終サイドカー保存の間にサーバーがクラッシュすると、復旧は `pending_user_message`、`active_stream_id`、`.json.bak`、`_index.json`、`state.db` から何が起きたかを推測する必要があります。これらの safeguard は有用ですが、事後に意図を再構築しているに過ぎません。

欠けているプリミティブは、ターン用の小さな write-ahead ジャーナルです。ワーカー開始前に送信されたユーザーターンを耐久的に記録し、ターンの進行に応じてジャーナルを進めます。

## Goals

- プロバイダーやワーカーの作業が始まる前に、添付メタデータを含む正確なユーザー送信ターンを保持する。
- クラッシュ復旧を決定論的にする: 送信済みだが未完了のターンを、推測なしに報告または再構築できる。
- ジャーナルの追記/更新形式を、起動時復旧、CLI 監査、将来の API 修復エンドポイントに十分単純に保つ。
- 復旧をバックグラウンドデーモンに変えない。これはストレージ衛生であり、長寿命サービスではない。

## Non-goals

- `state.db.sessions` や WebUI JSON サイドカーの置き換え。
- 全トークンや全 SSE イベントのジャーナル化。
- ツール呼び出しやプロバイダーストリームのリプレイ。
- 曖昧なクラッシュ後にアシスタントメッセージを自動でっち上げ。

## 提案ストレージ

既存の WebUI 状態エリア下に、セッションごとに1つの JSONL ファイルを使う:

```text
<SESSION_DIR>/_turn_journal/<session_id>.jsonl
```

各行は不変イベント。復旧は `turn_id` でスキャンし、最新のステータスを選べます。

### イベントの形

```json
{
  "version": 1,
  "event": "submitted",
  "turn_id": "20260511T001122Z-abcdef",
  "session_id": "abc123",
  "stream_id": "stream-xyz",
  "created_at": 1778458282.123,
  "role": "user",
  "content": "...",
  "attachments": [],
  "workspace": "/workspace",
  "model": "openai/gpt-5",
  "model_provider": "openai"
}
```

同じ `turn_id` の後続イベント:

```json
{"version":1,"event":"worker_started","turn_id":"...","created_at":1778458283.0}
{"version":1,"event":"assistant_started","turn_id":"...","created_at":1778458284.0}
{"version":1,"event":"completed","turn_id":"...","created_at":1778458299.0,"assistant_message_index":12}
{"version":1,"event":"interrupted","turn_id":"...","created_at":1778458301.0,"reason":"server_startup_recovery"}
```

## ターン状態機械

```text
submitted -> worker_started -> assistant_started -> completed
submitted -> interrupted
worker_started -> interrupted
assistant_started -> interrupted
```

`completed` は終端。`interrupted` は、後の明示的な修復が新しいターンを作らない限り終端。復旧はプロバイダー呼び出しを黙って再開すべきではない。

## 書き込みルール

1. `/api/chat/start` または同等のターン送信経路で:
   - `turn_id` を生成、
   - `submitted` を追記、
   - ジャーナルファイルを fsync、
   - その後初めてワーカーを開始。
2. ワーカースレッドが `_run_agent_streaming` に入るとき、`worker_started` を追記。
3. アシスタント出力が最初に永続化されるか明確に始まるとき、`assistant_started` を追記。
4. アシスタント回答を含むサイドカー保存が成功した後、`completed` を追記。
5. キャンセルまたは既知のワーカー例外で、理由付きで `interrupted` を追記。

## 同期耐久性設計の根拠

`submitted` イベントは今日、各書き込みで同期 `fsync` を使います。これはレイテンシとクラッシュ安全性保証の間の意図的なトレードオフです:

### なぜ submitted イベントは同期か

`submitted` イベントは復旧物語全体の耐久性アンカーです。ワーカー開始前にサーバーがクラッシュすると、ジャーナルはユーザーメッセージが受信されたことを反映する必要があります。非同期書き込みはその保証を失うリスクがあります: fsync していない書き込み直後のクラッシュは、`pending_user_message` がまだ存在するのにジャーナルを沈黙させ、復旧中の曖昧さを生み得ます。現在の設計は、ターン送信ごとに1回の追加ディスクラウンドトリップのコストで、その曖昧さを避けます。

### ストレージタイプ別のレイテンシ期待

報告される fsync レイテンシはストレージバックエンドで大きく異なります。心に留めるべきおおよその定性的範囲:

- **SSD（NVM/NVMe）**: 1桁ミリ秒。現代ハードウェアで p99 は通常 10 ms を十分下回る。ほとんどのターン送信は 5 ms 未満のオーバーヘッド。
- **回転ディスク（HDD）**: シーク時間が支配的。p50 約 5〜15 ms、負荷下で p99 は 50〜100 ms に達し得る。多数の並行送信を持つ忙しいサーバーはキューイング効果を見得る。
- **Docker/overlay ファイルシステム**: fsync レイテンシはコンテナストレージドライバとバッキングホストファイルシステムに依存。write-through と copy-on-write のセマンティクスが追加オーバーヘッドを導入し得る。典型的なコンテナ化デプロイで p95 は 10〜50 ms かもしれないが、正確な数字は構成とホスト負荷で変わる。

これらの範囲はオーダーオブマグニチュードのガイダンスであり、ベンチマークではありません。正確な数字はハードウェア、カーネルバージョン、ファイルシステムのマウントオプション、並行負荷に依存します。測定された証拠なしに特定のミリ秒の主張をドキュメントにコミットしないでください。

### メンテナ向けベンチマークガイダンス

同期書き込みがボトルネックだという証拠があれば、何かを変える前に測定してください:

1. `append_turn_journal_event` ヘルパーを計装し、各イベントタイプ（submitted、worker_started など）の実時間を記録。
2. 代表的なワークロードで p50/p95/p99 の追記/fsync レイテンシを捕捉（例: 現実的な並行性下で少なくとも 1,000 の submitted ターン）。
3. fsync 成分を分離: Linux では `strace -e fsync` またはカーネルトレース（`ftrace`、`perf`）で時間がどこで費やされるか確認。
4. パターンを確認: ほとんどの送信が 5 ms 未満だが、時折のディスク競合で p99 が 200 ms なら、非同期書き込みは tail を助けるが median は助けない。トレードオフは復旧保証の文脈で評価する必要がある。

### 将来のフォローアップ: 非同期ライフサイクルイベントジャーナル化

ジャーナル書き込みを非同期にするのは有効な将来の最適化ですが、次を要します:

- 信頼できるフラッシュ戦略（例: N 秒ごとの時間境界フラッシュ、セッションクローズ時フラッシュ、K 保留イベント後フラッシュ）。
- 部分フラッシュウィンドウを扱う復旧ロジック: フラッシュ前にクラッシュが起きると、最後の数件の submitted イベントがジャーナルから欠ける可能性。復旧はその曖昧さを考慮する必要がある。
- クラッシュ注入下でフラッシュの正しさを検証するテスト。

非同期ジャーナル書き込みは初期実装の一部 **ではありません**。同期ベースラインが安定だと証明され、復旧セマンティクスがよく理解された後のフォローアップ RFC に属します。

## 起動時復旧セマンティクス

起動時、各ジャーナルファイルについて:

- 最新イベントが `completed`: 何もしない。
- 最新イベントが `submitted` か `worker_started` で、サイドカーに一致するユーザーメッセージが存在しない:
  - 復旧マーカー付きでユーザーメッセージをセッションサイドカーに追記/復旧。
- 最新イベントが `submitted`、`worker_started`、`assistant_started` で、完了したアシスタントターンが存在しない:
  - 偽のアシスタント回答ではなく、可視の割り込みマーカーを追加。
- 既存の `.json.bak` と `state.db` の復旧が依然先に動き、ジャーナル調停の前にサイドカーが可能な限り完全になる。

## 監査の追加

`audit_session_recovery()` は次を報告できます:

- `turn_journal_pending_turn` — ユーザーメッセージがサイドカーに無ければ修復可能。
- `turn_journal_interrupted_turn` — 可視マーカーがあるかどうかで ok/warn。
- `turn_journal_malformed_event` — 手動レビュー。

safe repair は、ジャーナルイベント内容が有効な JSON でターゲットメッセージが不在のときのみ、送信されたユーザーメッセージと割り込みマーカーを実体化すべきです。

## API サーフェス

初期の読み取り専用エンドポイントは既存の復旧監査に折り込める:

```text
GET /api/session/recovery/audit
```

後で必要なら:

```text
GET /api/session/turn-journal?session_id=<id>
```

後者は診断専用とし、大きな添付ペイロードを伏字化または省略すべきです。

## Rollout plan

1. バックアップ/サイドカー復旧と監査プリミティブを着地させる。
2. このジャーナルライターを、config フラグなしでターン送信経路に追加。ローカル限定・追記のみ。
3. 保留ジャーナルターンの読み取り専用監査レポートを追加。
4. 欠けたユーザーメッセージと割り込みマーカーの safe repair を追加。
5. 安定したら、保持ウィンドウより古い completed ジャーナルエントリの剪定を検討。ただしサイドカー/インデックス復旧に findings がない後のみ。

## Open questions

- ブラウザリトライとサーバーリトライが同じユーザーメッセージを重複させないよう、`turn_id` を定義する正確な場所。
- 添付ファイルが独自の耐久マニフェストエントリを必要とするか、v1 ではメタデータのみで十分か。
- `assistant_started` 後 `completed` 前に、アシスタントの部分出力をどの程度復旧可能にすべきか。
- completed ジャーナルエントリをセッションごとのチェックポイントファイルに圧縮すべきか。

## 最小実装スライス

最初の実装 PR は意図的に小さくすべき:

- ヘルパー: `append_turn_journal_event(session_id, event)`
- ヘルパー: `read_turn_journal(session_id)`
- アトミック追記、malformed-line 耐性、状態導出のユニットテスト
- 1つの呼び出し箇所: ワーカー開始前に `submitted` を追記
- 保留ジャーナルターンの監査のみのレポート

最初の実装に replay/repair を組み合わせ **ない** こと。Replay は WAL システムのバグの大半が住む場所。まずライターと監査を出荷し、形式を証明し、その後 repair を追加する。
